# Monix: One File, Zero Setup

Eight months ago, a developer posted on the jupyenv GitHub: "Is this project still maintained?" Jupyenv was Tweag's ambitious attempt to bring Nix-powered reproducibility to Jupyter notebooks. The response was candid: "pretty dormant... some architectural choices did not pan out."

The last comment in [that thread](https://github.com/tweag/jupyenv/issues/543)? That was me. I'd moved on to Marimo, and I thought I'd found the answer to notebook reproducibility.

marimo solves a lot - pure Python, git-friendly, works well with modern tooling.
But I'd spent years fighting with Jupyter and Bazel builds, and I still ran into issues.
Nix reproducibility is just a step above: content-addressed store, lockable dependency graph, the five-year guarantee.

The thing is, marimo already has great Python package management. That covers 95% of use cases. But I kept wondering: could you bridge that with Nix's system-level reproducibility without building something as complex as jupyenv?

Turns out, you can.

## The system dependency problem

There's been real progress on notebook reproducibility. [Marimo stores notebooks as pure Python](https://marimo.io/blog/python-not-json), making them git-friendly and testable.
[PEP 723](https://docs.astral.sh/uv/guides/scripts/) lets you embed dependencies right in your script.
[Jupyenv tackled the full environment problem](https://www.tweag.io/blog/2023-02-02-jupyenv-0-1-0/) with Nix, though the complexity was hard to sustain.

But there's a gap. PEP 723 handles Python packages:

```python
# /// script
# dependencies = [
#     "marimo",
#     "matplotlib==3.9.2",
# ]
# ///
```

What about ffmpeg? What about nodejs? System dependencies exist outside the Python packaging world. There's [an issue for pixi support](https://github.com/prefix-dev/pixi/issues/3751), but no public-facing progress.

And honestly? Nothing beats Nix. It's really that good. The entire dependency graph - from your script down to libc - is content-addressed and reproducible. Five years from now, that flake reference will build the exact same environment.

The question was whether I could make it simple enough to actually use.

## One file

I wanted to see if I could make a completely self-contained notebook. Not just Python dependencies, but system dependencies too. No setup, no README with installation instructions, no Docker container to build. Just one file that runs.

Here's what that looks like:

```python
#!/usr/bin/env nix
#!nix shell --impure --expr ``(
#!nix   builtins.getFlake "github:dmadisetti/monix"
#!nix ).lib.moEnv {
#!nix   deps = ["ffmpeg"];
#!nix   features = ["lsp"];
#!nix   mode = "notebook";
#!nix   script = ./bayes_theorem.py;
#!nix }`` --command monix
# /// script
# requires-python = ">=3.9"
# dependencies = [
#     "marimo",
#     "matplotlib==3.9.2",
# ]
# ///

import marimo
# ... your notebook code
```

Make it executable and run it:
```bash
chmod +x bayes_theorem.py
./bayes_theorem.py
```

The script bootstraps its own environment. System dependencies, Python packages, everything.

This works because shebangs are file-level magic on Unix systems - the kernel reads the first two bytes, sees `#!`, and uses the rest of the line to determine how to execute the file. Nix extends this with [multiple `#! nix` lines](https://github.com/NixOS/nix/blob/35d7719f4649b74a604ac78edd76ff5bd2b564a2/src/nix/nix.md#L263) to build an entire environment before the script runs. The documentation is sparse, but if you're willing to dig through the C++ source, it's all there.

I've seen this self-contained pattern in a few places - [Docker shebangs](https://hugojosefson.github.io/docker-shebang/) do something similar. Single file by definition has less footprint than multiple files, and the composability is excellent. With Nix, you get true reproducibility without container overhead - the script references a flake, Nix builds the environment, and everything is content-addressed in the Nix store.

## Two modes

The same script can work in two different modes. You can leverage uv by itself, which allows for dynamic imports and leans into the infrastructure built into marimo:

```nix
moEnv {
  deps = ["ffmpeg"];
  features = ["lsp"];
  mode = "notebook";
}
```

Nix handles system dependencies, uv handles Python packages. Fast iteration, reproducible system environment.

Or you can use uv2nix for the full Nix treatment:

```nix
moEnv {
  deps = ["ffmpeg"];
  features = ["lsp"];
  mode = "notebook";
  script = ./bayes_theorem.py;
}
```

Everything goes through Nix. The complete dependency closure, all locked in the Nix store. This is what you want for containers or long-term archival.

It's a bit of a purity hack - the only immediately obvious way to get this working is by providing the filename to the shebang call. If you can figure out something better, let me know.
